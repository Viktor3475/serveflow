# Phase 5 — QR menus and ordering

The application now supports a public table menu, customization, a cart, customer/waiter submissions and private receipts. It builds on Phase 4's staff management and existing SQL schema. No new migration is required. Kitchen status updates and SignalR remain Phase 6.

## Start and use it

1. Complete the [database](phase-2-database.md), [staff](phase-3-authentication.md) and [management](phase-4-management.md) setup. Apply both existing migrations and provision an administrator.
2. Restore/build and run the Web project. Add categories and products through **Menu**. On a product's edit page select **Manage product options** to add optional extras and their price per item.
3. Configure `Ordering:PublicOrigin` (environment variable `Ordering__PublicOrigin`) to the externally reachable HTTPS origin, for example `https://orders.example.com`. The origin must have no path beyond `/`, credentials, query or fragment. Production QR generation rejects missing/invalid configuration. Development defaults to `http://localhost:5080`; a phone cannot reach another machine's localhost, so configure a reachable development origin when testing a physical scan. Browser Web Crypto requires HTTPS or localhost.
4. Open **Tables → QR code → Generate and download SVG** as administrator. Print the downloaded SVG for that table. Each generation rotates the token; generating again invalidates earlier printed codes and table sessions. Reload the QR page before another generation because the rowversion changed.
5. Scan the printed code. The browser exchanges its fragment token for a protected two-hour table cookie, then opens the digital menu. Search/filter dishes, select extras, enter item instructions, adjust quantities and add order notes.
6. Review the total and press **Send order**. The private receipt link shows immutable item/option prices and the order's current status. Keep that link; its fragment is a capability granting receipt access. It does not grant order editing or payment actions. Status refresh is manual in this phase.
7. A waiter or administrator can use **Tables → Create order** to use the same cart without a customer QR session. The service checks the stored staff role and restaurant; submitted actor/restaurant IDs cannot change ownership.

The browser requires JavaScript, Web Crypto and session storage. Cart state stays in that browser tab and is scoped to the table and customer/staff endpoint. Switching tables does not mix carts. A refresh reviews current product/option prices; stale versions or unavailable selections are rejected on submission. Amounts shown in the cart are estimates; the server calculates the persisted total. Payment processing is not part of order submission.

## Security and consistency

QR codes contain 32 cryptographically random bytes encoded as lowercase hex. SQL stores only their SHA-256 hash. The raw code is returned only in the generated SVG. QR links use a configured origin, never the request Host. Their secret is a URL fragment, removed from browser history before the exchange POST; it never appears in the normal HTTP request URL. Exchange and order POSTs require antiforgery tokens. Table cookies use Data Protection, HttpOnly, SameSite Strict, an absolute two-hour expiry, and Secure in production. Each database operation rechecks the active restaurant/table and current token hash, so rotation/archive revokes existing access.

Receipt secrets are independently generated by browser Web Crypto and sent in the order body; SQL stores only their hash. Receipt reads/recovery require the secret in `X-Receipt-Token`. Receipt URLs put the secret in the fragment. Customer routes and staff API responses use `no-store`; customer/QR routes set `no-referrer`. Do not configure a proxy or telemetry collector to log bodies, cookies or capability headers.

Order requests carry IDs, original menu/option rowversions, quantities and text; they carry no trusted prices. The validator permits 1–50 lines, 1–20 units per line, at most 100 units total and at most 10 distinct options per line. Notes are bounded to 1000 characters, item instructions to 500, and JSON requests to 32 KiB. The server rejects unavailable/archived/cross-product options and unavailable/archived products/categories. Changed rowversions require the customer to refresh and review the cart. All monetary values use decimal on the server and snapshots in order rows.

Order creation uses a retry-aware serializable SQL Server transaction and an update lock on the target table. It verifies access, checks the table-scoped idempotency key, loads current products/options, calculates the total, writes the order/items/options/initial Pending history and marks the table Occupied before commit. A reserved table rejects customer submissions; authorized staff can create its order. Cross-table/cross-restaurant access is rejected. No order-edit endpoint is introduced in this phase.

Submission keys are canonical random UUID strings. A fingerprint binds the exact cart, versions, trimmed instructions/notes and receipt-secret hash. Repeating the same key and payload returns the original order; changing the payload returns 409. The SQL unique index is a further safeguard. The cart freezes a pending submission on network/unknown server failure and retries the same payload. Before retry it can recover an already committed order through the private receipt secret. Confirmed rejection clears the pending attempt so the cart can be corrected. The raw pending secret/key are retained in tab storage until confirmation.

The total is bounded to 1,000,000 currency units per order. QR exchange and order endpoints allow 10 requests per minute per IP; public data reads allow 120 per minute per IP. Customer creation is also limited to 10 orders per table per 15 minutes inside the transaction. Idempotent replays are checked before this limit. Authorized staff bypass the persisted customer creation limit, while retaining the HTTP request limit. These process-local HTTP limits are not a distributed rate limiter; a multi-instance deployment should also enforce limits at its gateway.

QR images use centrally pinned [QRCoder 1.8.0](https://www.nuget.org/packages/QRCoder/1.8.0), rendering SVG without System.Drawing. Product images still use the bounded private store from Phase 4; anonymous reads require a valid scoped table session. Product option management uses administrator membership, ownership filters, rowversions and archive/restore instead of physical deletion.

## API routes

| Route | Behavior |
| --- | --- |
| `POST /api/dining/session` | Exchange `{ token }` with CSRF for the protected table cookie |
| `GET /api/dining/menu` | Current table menu, prices, versions and options |
| `POST /api/dining/orders` | Validate/create or replay an order; CSRF required |
| `GET /api/dining/receipts/{id}` | Private receipt with `X-Receipt-Token` |
| `GET /api/dining/receipts/recover` | Recover an order by its private receipt token after a lost response |
| `GET /Dining/Image/{id}` | Scoped product image through the table session |
| `GET /api/staff/tables/{id}/menu` | Administrator/waiter menu within their restaurant |
| `POST /api/staff/tables/{id}/orders` | Administrator/waiter submission; CSRF required |
| `POST /TableQr/Generate/{id}` | Administrator-only rotate/download; original rowversion and CSRF required |

Order creation returns 201; an identical replay returns 200. Invalid input returns 400, expired/wrong table access 403, stale/changed content or reserved table 409, and exceeded limits 429. Receipt failures return 404 without revealing the order. Expected errors contain a simple `error` message. Staff cookie challenges can redirect to login/access-denied. Unhandled faults retain the host's sanitized Problem Details behavior.

## Tests and remaining verification

```bash
dotnet restore ServeFlow.sln --locked-mode
dotnet build ServeFlow.sln --no-restore -c Release
dotnet test --solution ServeFlow.sln --no-build -c Release
dotnet ef migrations has-pending-model-changes --project src/ServeFlow.Infrastructure --startup-project src/ServeFlow.Web --configuration Release --no-build
```

Pricing/validation tests run without SQL. HTTP tests execute real MVC, cookies/Data Protection, CSRF, throttling and SVG generation with a fixed ordering backend. They prove web behavior, not database transactions. Seven new opt-in SQL Server cases cover snapshots/history/occupancy, simultaneous identical submissions, changed-key conflicts, real cross-table/restaurant rejection and QR rotation, unavailable selections, waiter permissions/reserved tables, and transactional customer limits. They create/drop only generated test databases. Configure `SERVEFLOW_TEST_SQLSERVER` on a dedicated test instance using the Phase 2 instructions. No live SQL Server connection is currently configured in this workspace; database tests explicitly skip. See [verification](verification.md) for actual executed checks.

SignalR, kitchen transitions and automatic status updates come next. Live SQL Server concurrency/commit behavior and a physical browser/phone QR workflow still require execution before a production release. There are no automatically seeded credentials, payment claims or deployment actions in this phase.
